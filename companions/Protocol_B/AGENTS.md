# Agent instructions for Protocol_B

## Selected assurance level

Targeted independent review. A non-author checks the review selection. Independently review selected novel or fragile arguments, essential checkers and substantive repairs. Record author-only regions. Do not silently expand the selection into a Protocol_D completeness audit.

## Start small

Read PROTOCOL.md and PROJECT.md. The selected protocol states the assurance requirements. These instructions organize the work without changing them. Initialize one canonical ledger alongside the first proof work. Begin with REVIEW_LEDGER.md or an existing adequate implementation; use a small script only for a concrete validation need.

Do not build a custom service, GitHub App, dashboard or general review engine unless requested or a demonstrated requirement cannot be met more simply. Do not turn an archive or hash update into a separate research project.

## Use meaningful units and one owner

Record a coherent lemma, application, construction or interface once. Give it stable identifiers and list its actual consumers. A checklist is a view of the evidence, not a requirement to restate the same proof many times. Group uses only when the same argument truly covers them.

Use one integrator and one selected candidate. Before assigning work, check for an active owner or an existing accepted result. If parallel work is authorized, assign bounded tasks with fixed inputs, disjoint output files and explicit acceptance criteria. Reviewers assess the exact delivered candidate. Do not spawn workers merely to repeat completed checks.

## Keep accepted work accepted

Bind review to mathematical statements, definitions, assumptions, proofs, source versions and consuming context. For a change, identify affected units and downstream uses. Reopen those units and the necessary composition checks. Preserve decisions on genuinely unaffected work.

A moved passage or changed line number usually needs a scoped binding update rather than a new mathematical derivation. A changed definition can invalidate an unchanged paragraph. Cache checks by their complete relevant inputs and checker version. Preserve earlier decisions; never replace their hashes to manufacture a fresh review.

## Keep trust and evidence honest

Apply the selected framework's trust boundary. For A through E, do not reprove published literature without a concrete reason beyond the required source, convention and applicability checks. For F, the entire mathematical dependency closure needs formal proofs, which may come from pinned libraries.

Every known substantive objection enters the ledger. Separate an invalid inference from an unperformed review, a source-access problem or an accepted repair awaiting incorporation. Report each at its actual scope. Do not declare completion from token counts, agent counts, file counts or an arbitrary percentage.

Record human and model review provenance honestly. Non-author review does not mean independent reasoning is guaranteed. If a reviewer writes a substantive repair, use a different reviewer when independent acceptance is required by the chosen protocol.

## Finish the specified task

State acceptance criteria before work. After they pass, finish the task. Reopen it for a changed premise, concrete finding or demonstrated omission, not because another review is possible. Do not recursively demand reviews of unchanged review prose.

Keep mathematical work, incorporation, and mechanical release work separate in status reports. Build the cumulative handoff once the research release is ready, then synchronize it with the manuscript, inventory, findings and artifact index. Do not rebuild every archive after every internal edit.

Tool failures need one recovery owner and bounded retries. Never replay a possibly live writer without checking its state. Preserve useful drafts and errors, and continue independent work when possible.

Existing user authorizations remain valid. Publication, external messaging, purchases and access changes still require the appropriate authorization. These templates grant none of them by themselves. Do not send credentials or unrelated private files to reviewers or release archives.
